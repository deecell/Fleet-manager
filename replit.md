# Deecell Fleet Tracking Dashboard

## Overview
The Deecell Fleet Tracking Dashboard is a real-time monitoring system designed for managing a fleet of clean energy trucks. It provides comprehensive visibility into truck locations, battery states, performance metrics, and system health. Key capabilities include tracking individual vehicles, viewing historical data, receiving notifications, and calculating fuel cost savings from solar energy. The project aims to provide a data-heavy enterprise application with a clean, minimalistic design for efficient fleet management.

## System Architecture

### Frontend
The frontend uses React 18 with TypeScript and Vite, Wouter for routing, and TanStack React Query for server state. UI components are built with Radix UI primitives and shadcn/ui patterns, styled with Tailwind CSS for a consistent, responsive design with light/dark modes. Data visualization is handled by Recharts, and map integration uses static images with SVG overlays. Form validation is managed by React Hook Form with Zod.

### Backend
The backend is built with Node.js and Express.js, leveraging TypeScript for type safety and Zod for data validation. It exposes a RESTful API and uses an abstracted `IStorage` interface implemented with PostgreSQL for data persistence, supporting multi-tenant queries.

### Data Storage
PostgreSQL with Drizzle ORM and Neon serverless driver is used for data storage. Drizzle Kit manages the schema, and `connect-pg-simple` handles PostgreSQL-backed sessions. The database includes tables for Organizations, Users, Fleets, Trucks, Devices, and various performance and alert data. Multi-tenancy is enforced with `organization_id` and row-level security.

### Design System
The design system features a neutral-based color palette with a green primary accent, rounded cards, hover elevation, and a badge system. It emphasizes a consistent spacing system and a mobile-first responsive design approach.

### Authentication
Both admin and customer authentication are session-based and use email/password with bcrypt. Platform admins are real `users` rows in the `Deecell Internal` org (slug `deecell-internal`) with `is_platform_admin = true`; the legacy shared `ADMIN_PASSWORD` is no longer accepted for login and is no longer a fallback for `SESSION_SECRET`. `SESSION_SECRET` is now the only source of the session secret — production fails fast at startup if it is unset, dev falls back to a labelled insecure string with a warning. `ADMIN_PASSWORD` lives only as the gate for the one-shot `/api/migrate-database` endpoint in `migration-routes.ts`. `platformAdminMiddleware` re-validates the user on every admin request — checking `isPlatformAdmin`, `isActive`, and the org's `isActive` flag — so revoking an admin takes effect immediately. Andy (`andy@deecell.com`) is seeded by the production migration script with a NULL `password_hash`; the same script also mints an invitation token and emails Andy a one-click password-setup link via SendGrid. The app boot is an idempotent fallback that re-mints + re-sends if the migration's email step fails. Additional admins are invited from `/admin/users` (Manage Platform Admins panel), which creates a user row with `is_platform_admin = true` and emails them an invitation token; promoting an existing deecell-internal user with NULL password also auto-issues an invitation email for parity. `tenantMiddleware` ensures active user/organization verification for the customer surface. Invitation tokens expire in 7 days; admins can resend a fresh token from the `/admin/users` row (icon next to "Never" in Last Login) or from the Manage Platform Admins panel via `POST /api/v1/admin/organizations/:orgId/users/:userId/resend-invitation` and `POST /api/v1/admin/platform-admins/:id/resend-invitation`. Both endpoints reuse the same `invitation_tokens` table + `sendInvitationEmail` pipeline as the create-user flow, reject the request when the user already has a `password_hash` (use password-reset instead), require `isEmailConfigured()` (503 otherwise), and apply a 60-second per-user in-memory cooldown to absorb double-clicks (429 on hit). Old superseded tokens are left in place — the `accept-invitation` route already filters by `expires_at > now() AND used_at IS NULL`.

### Device Registration (Task #21)
SIM linkage is now established **synchronously and fail-loud at admin "Register Device" time**, not by the periodic SIMPro sync + InHand poller race. A complementary per-device **"Refresh SIM from Wireless Logic"** action (`POST /api/v1/admin/devices/:id/refresh-sim`, surfaced as a rotating-arrow icon on each `/admin/devices` row) handles the **router-swap lifecycle**: when a physical InHand router (and its SIM) is replaced in the field, the operator clicks Refresh on that device and the server re-runs the same strict-single `simProClient.getSimByDeviceName()` lookup. On a single match it updates the device's existing `sims` row in place — even if the ICCID changed — in a single transaction. ICCID drift is handled three ways: (1) if a row with the new ICCID already exists (typically created by the periodic SIMPro sync) we claim it and unlink the old current row by nulling its `deviceId`/`truckId` (kept for `data_used_mb` history, not deleted); (2) if no row exists with the new ICCID, the current row is overwritten in place; (3) if neither exists, a fresh row is inserted. When the ICCID actually changes the endpoint also clears `router_rssi`/`router_signal_updated_at` on the active row so the UI shows `--` until the next InHand poll repopulates from the new router (~2 min). The endpoint reuses the same structured error codes as registration (`SIM_NOT_FOUND` / `SIM_MULTIPLE_MATCH` / `SIM_ALREADY_LINKED`/409) and applies the same no-silent-steal rule — if the new ICCID is linked to a *different* device the call is rejected and the operator must detach in the Wireless Logic console first. The result dialog shows a before/after diff (ICCID/MSISDN/IMSI). The original registration flow is unchanged: `POST /api/v1/admin/organizations/:orgId/devices` requires a `deviceName`, then calls Wireless Logic via `simProClient.getSimByDeviceName()` (a strict-single discriminated helper in `server/services/simpro-client.ts`) before inserting the device row. Zero matches return 400 `SIM_NOT_FOUND`, multiple matches return 400 `SIM_MULTIPLE_MATCH`, and the single-match happy path runs `db.transaction` containing the device insert + an `iccid`-keyed `sims` write that pre-checks for an existing row: if one exists with `device_id` set to a *different* device the request is rejected 409 `SIM_ALREADY_LINKED` (no silent reassignment); otherwise an unlinked existing row is `UPDATE`d in place or a brand-new row is `INSERT`ed. Device + SIM are committed atomically — no half-linked state ever exists. The `/admin/devices` form keeps the dialog open on those structured errors and renders an inline alert so the operator can fix the name and retry. A separate idempotent admin endpoint `POST /api/v1/admin/devices/backfill-sim-links` (surfaced as a "Backfill SIM Links" button on `/admin/devices`) runs the same strict-single lookup sequentially for every PowerMon device with no linked SIM, returning a per-bucket summary `{ scanned, linked, skipped_no_name, failed_no_match, failed_multiple_match, failed_api_error }` rendered in a dialog. The InHand poller (`device-manager/app/inhand-poller.js`) gained `device_name` as a 4th match key (case-insensitive) after `iccid`/`imsi`/`msisdn` as belt-and-suspenders for legacy devices. The periodic SIMPro sync still uses the loose `getSimsByDeviceName` helper to refresh `data_used_mb`/`last_location_update` for the whole catalog — only registration is strict. The sync's existing-row UPDATE branch preserves the row's current `deviceId`/`truckId` and never re-links from `custom_field1`; the authoritative link-establishment paths are registration, the Refresh button, and the Backfill button. (Without this preservation, a row that Refresh intentionally detached during a router swap would get silently re-linked on the next sync tick while the old SIM is still active in Wireless Logic, reverting the swap.) Fresh-insert auto-linking from `custom_field1` still happens for SIMs that show up in Wireless Logic for the first time.

### Device Manager
A standalone Node.js application manages device polling and data collection (PowerMon devices, SIM cards, GPS). It's designed for AWS EC2 and uses a supervisor/worker architecture with cohort-based sharding for fault isolation. **Midnight firmware mass-close (2026-06-24)**: at ~00:00 UTC the PowerMon-W firmware closes every live session at once (reason=2); the synchronized reconnect storm is accept-then-instant-closed (0–5 ms) by the still-settling firmware, which previously tripped the flapping breaker fleet-wide and wedged reachable trucks into "No data". A reason=2 close of a real (≥200 ms) session now opens a 2-minute **firmware-recovery window** (`FIRMWARE_RECOVERY_WINDOW_MS` in `connection-pool.js`): instant rejects inside it are logged but NOT counted toward the breaker, and every reconnect is spaced to `FIRMWARE_RECOVERY_RECONNECT_DELAY_MS` (20 s, time-based so it survives the connect→instant-drop cycles that reset `reconnectAttempts`). The window is cleared on the next successful poll; a device still instant-dropping after it expires trips the breaker as before. The shared `flapping-verdict.js` `classifyFlappingVerdict()` takes `opts.powerMonConnected` — a completed PowerMon connect is direct proof of reachability and forces "PowerMon-side flap", never "Router/cellular outage", regardless of stale router-signal/GPS age (the breaker-open FLAPPING DIAGNOSTIC passes `true`; the connect-failed CLI passes `result.success`; the probe-failed supervisor path passes `false`; the removed `routerReachable` ping was NOT reintroduced). **Orphaned probing reconciliation**: a probe sets `connection_status='probing'` but tracks its live worker only in the supervisor's in-memory `probeWorkers` map, so a supervisor crash mid-probe or a failed exit-handler DB write stranded the row forever; `startupRecoverySweep` now also resets orphaned `probing` rows → `flapping`, and the periodic `supervisor._probeFlappingDevices` loop calls `db.reconcileOrphanedProbing(activeSerials)` to reset any `probing` row with no live worker → `flapping`. A one-time `scripts/migrations/2026-06-24_unstick_probing.sh` resets the already-wedged fleet (`probing`/`flapping`/`unstable` with active credentials → clean slate). It integrates with `libpowermon_bin` (Thornwave's C++ library), polls various devices at different intervals, and includes a circuit breaker mechanism for isolating problematic devices and recovering them via solo probe workers. **Per-poll watchdog (2026-05-20)**: `polling-scheduler.js` `pollDevice` wraps `conn.poll()` in an 8 s `Promise.race` timeout. The native PowerMon API is callback-based (`device.getMonitorData(cb)`) and on PowerMon-W firmware 1.35 the callback can silently never fire after a successful TCP connect — without a per-poll timeout, that hangs `Promise.allSettled` in `processTick` forever and freezes the entire cohort's scheduler. On timeout the scheduler logs, calls `conn.disconnect(false)` + `conn.scheduleReconnect()`, and returns null so the tick completes; the next tick reconnects the device fresh. This restores the watchdog property that the pre-Phase-1 `process.exit(1)` defense was incidentally providing, scoped to one poll instead of the whole worker. **Connection-state taxonomy (2026-05-14)**: rapid-disconnect detection uses honest names — `flapping` (≥2 instant disconnects <200ms — replaces legacy `no_power` + `weak_signal`), `unstable` (≥3 rapid disconnects, none instant), `probing` (solo probe in progress), `offline` (admin-set only), and the normal poll-lifecycle states. The 1st instant-disconnect is logged as an early warning but no longer persists any DB state — only an opened circuit breaker writes `flapping`/`unstable`. When the breaker opens, the worker isolates the bad device locally (nulls its native ref + writes DB state) and stays alive — the previous "set `nativeLibraryShutdown=true`, null every pool member, and `process.exit(1)` after 3 s" defense was retired after 30+ days of prod logs (us-east-2) showed zero SIGABRT/SIGSEGV/core-dumps; it was killing healthy cohort-mates to solve a problem that wasn't happening. Recovery is handled by the supervisor's solo-probe loop (one process per flapping device, 5-min quarantine, exponential backoff `[5,15,60,240]` minutes) so a probe crash never affects healthy cohort siblings. The legacy `nativeLibraryShutdown` flag + its read-side guards remain in place as cheap dead-code defense-in-depth in case a real native abort ever materializes. The InHand poller (`device-manager/app/inhand-poller.js`) talks to `https://iot.inhandnetworks.com` (the global Device Manager API — the `na.inhandcloud.com` regional hostname is DNS-dead and was retired by the 2026-05-13 migration) and extracts both GPS coordinates and cellular signal strength on every poll: GPS updates land on `trucks` (when a truck is assigned and coords are present), and signal strength always lands on `sims.router_rssi` + `sims.router_signal_updated_at`. Signal extraction is two-stage: first the bulk `/api/devices?verbose=100` response is parsed (dBm-first fields `device.rssi`, `info.signalStrength`, `device.signalStrength`, then ASU/CSQ 0–31 via `info.rssi`/`info.signalLevel`/`info.csq`/`device.signalLevel`/`info.signal` converted with `dBm = -113 + 2*asu`), then for every online device with a Mongo `_id` the poller calls the per-device endpoint `GET /api/devices/{_id}/signal?begin=&end=` (last 5 min, ASU 0–31, skip 99) and overrides the bulk value — this is required because IR302 firmware doesn't populate signal in the bulk response. Per-device fetches run ≤10 in-flight and tolerate per-device failures. The `/admin/devices` page surfaces this as a sortable color-coded "Router Sig" column alongside the existing PowerMon "PM Sig" column (both rendered via the shared `<SignalCell>` component using the cellular bands -70 / -85 / -100 dBm). For diagnosing InHand connectivity from a laptop without touching prod, `scripts/probe/inhand_signal_probe.sh` mirrors the same OAuth2 + `_extractRssi` logic and prints per-device signal rows (raw field name + normalized dBm) — useful when the in-prod verification step comes back empty. **GPS visibility & instrumentation (2026-06-24, Phase 1)**: truck location is now surfaced and measurable without any schema change (the data already lives on `trucks`). (1) `listAllDevicesWithSnapshots`/`listDevicesWithSnapshots` (`server/db-storage.ts`) batch-join `trucks` lat/lng/`location_description`/`last_location_update` onto each device by `truck_id` (per-org method scopes the join to the same `organization_id`), and `/admin/devices` renders a "Location" column (after "Router Sig") via the shared `<LocationCell>` component — reverse-geocoded address as a Google-Maps `maps?q=lat,lng` link, raw `lat,lng` to 5 dp so coarse jitter is visible, and an "x min ago" freshness line that greys/ambers when stale (`—` when no truck or no fix). (2) The PowerMon per-poll INFO line in `database.js` appends `loc=<address>` (`loc=--` when no fix) so power state and location read together. (3) The InHand poller adds a `haversineMeters()` helper (now reused by `hasCoordsMoved`) and logs a per-truck `GPS fix` line each poll with Δmeters / Δseconds / implied mph vs the prior `last_location_update`, characterizing accuracy (jitter when parked) and cadence (seconds between fixes). The DRIVING-vs-IDLING-vs-PARKED state machine that consumes these signals is deferred to Phase 2.

### Savings Calculation System
This system calculates fuel cost savings from solar energy using a formula that integrates solar energy data and regional diesel prices fetched from the U.S. Energy Information Administration (EIA) API.

### Fleet Export Pipeline
An asynchronous pipeline handles CSV/Excel exports of fleet snapshots and historical time-series data for individual trucks (per-minute, hourly, or daily granularity, up to 1 year, 600k row cap). It uses dedicated services for cell building and serialization, stores export jobs in a database, processes them with an in-process worker, uploads results to S3, and surfaces progress in the recent-exports table + `ExportsBanner`. **Email notifications are opt-in for every export type (customer + admin)** — each form has a default-OFF "Email me when ready" checkbox persisted on the job as `export_jobs.notify_by_email`; the worker only fires `sendExportReady`/`sendExportFailed` SendGrid emails when that flag is true, otherwise it silently skips. Historical aggregation reuses existing data sources — chassis voltage (`voltage2 < 13.0 V`) for parked/driving state and minutes, `sim_location_history` for per-bucket lat/long, and `savings_config` + `fuel_prices` for daily savings — so no new telemetry tables are required. Concurrency limits are enforced per user and organization.

### Admin Export Soft Launch
The same async export pipeline is also used by admin pages, gated by `adminMiddleware` instead of `tenantMiddleware`. The single admin surface is the dedicated `/admin/export` page, which combines the device-registry export with a per-truck historical export and a recent-exports table. (Earlier iterations also exposed an inline "Export" button and a per-row Download icon on `/admin/devices`; both were removed in favour of the consolidated `/admin/export` page, and the `AdminExportDialog` / `AdminTruckHistoryExportDialog` components were deleted.) Admin exports run through the same worker → S3 → email → sticky banner flow as customer exports. To plug into the existing pipeline without forking it, a synthetic "Deecell Admin" user inside a "Deecell Internal" org is bootstrapped on first admin login and reused as `export_jobs.user_id` / `organization_id`, so concurrency limits and email lookup keep working. The `export_jobs` table uses a `kind` column (`'snapshot' | 'historical' | 'admin_devices' | 'admin_historical'`) which the worker dispatches on; admin files land under `s3://…/exports/admin/<jobId>/<filename>`. For `admin_historical` jobs the worker reads the target customer org from `filters.organizationId` (the admin's Deecell Internal org stays on `job.organizationId` for concurrency accounting). `POST /api/admin/exports` accepts a discriminated `kind: 'devices' | 'historical'` payload; historical requests are validated against the same 1-year range and 600k-row caps as the customer-facing pipeline.

A natural language chat interface, powered by OpenAI GPT-4o-mini via Replit AI Integrations, provides fleet management queries and insights using function calling for real-time data access.
